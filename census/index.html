6 / 遮蔽物手前の層が、下の層の途切れを作る

作者の言明(2026-10-26):「手前側に何かがあると、その後ろ側のレイヤでは描かないで済ますことが多い。遮蔽物レイヤがあるということがわからないと、なぜ下のレイヤで何かが途切れているかわからない」 —— 下の層の線の途切れは、描き手が省いたからで、欠陥ではない。遮蔽物が分からないと、その途切れを「欠落」と読む。

作者の答(2026-10-27):「ラスタライズする。印については分からない」 —— だから 3D の層数は「3D を使った頁の数」ではなく、その下限。ラスタライズされた 3D は種別が raster になる。印が残るかは作者も知らない(「残らない」ではなく「不明」)ので、形式を知る抽出側へ回した。
そしてラスタライズされても、その層は遮蔽物のままである —— 名前と種別で見つかるのは遮蔽物の一部だけで、一般の判定は順序と不透明度と重なりで決まる(依頼8 がその材料)。

3D の経路は2つ(作者、2026-10-27):クリスタの 3D オブジェクト(レンダリングして画像化して確定。印は不明)と、blender でレンダリングした画像のインポート(自動処理で取り込む)。手元の15頁で経路2が見つかった —— 層名 rendering_<pass>_<位置><連番>(pass は base / shadow / lineart / render)。4層とも layer_type = 1 のラスタで、種別では普通のラスタと見分けが付かない。そして名前が出たのは層名で、フォルダー名ではなかったので、両方見る。rendering_lineart_* という pass が在る —— blender が線画を出している。

作者が挙げた4種は 3D / フキダシ(独立した層)/ ホワイト / 黒消し。そしてどの名前が遮蔽物かは作者が選ぶ —— 作者自身が white について「多いと思う」と言っている。層名はここには出さない(件数だけ)。

作者の指示(2026-10-27):「名前で見つけて統計量で裏付ける・統計量で見つけて名前で裏付ける。どちらの順でもいいが、層の見極めは片面だけで済ませない方がよい」 —— 3D に限らない規則なので、表の構造に入れた。

最初に選んだ素性(layer_type/composite/clip/has_mask)は失敗した —— 何も特徴づけていない(white の名前側 10層に対し、同じ素性の層が 824)。その失敗は下の表に残したまま、別の側を足した。素性を名前に合うまで調整しない:それは名前に素性を当てはめる作業で、両面の裏付けではなく片面を2回数えることになる。

6-3 / フキダシの両面 —— 仕組みから導いた素性

素性は「その層が物として何であるか」から導く。フキダシは不透明な白い面と、その輪郭である:白が最頻 / 色の段が2以下 / 彩度0 / 最頻色の占有が1未満(輪郭が在る) / 描画率 0.25 未満。節の理由を書けない節は入れない —— 理由の無い節は、名前に合わせて足した節と区別が付かない。

8頁の範囲で、名前側と素性側が同じ3層を指した(素性だけの層 0・名前だけの層 0)。そしてホワイトと分けているのは占有の節である —— フキダシは白い面と輪郭(占有 0.89)、ホワイトは白い面だけ(占有 1.00・色の段1)。その節を外すと、ホワイトと白い枠と下地が入ってくる(15層)。
5節のうち2節は何も落としていない(描画率の節は0層)。閾 0.5 と 0.25 はこちらが置いた数で、どちらも何も落としていない —— 下側 0.5 は 0.5〜0.887 に層が1つも無いので未検証。働いている境界は上側(1.00 を外す)だけである。

6-4 / そして遮蔽物であることは、順序の性質である

作者の言明に戻ると —— 「手前側に何かがあると、その後ろ側のレイヤでは描かないで済ます」。手前側であることが効いている。だから名前で集めた層が本当に手前に居るかを、依頼8 の構造の表で全 437,561層について測った。素性側(画素)は8頁しか届かないが、構造の側は全数に届く。

棒の前に帰無値を出す —— 「手前に寄っている」は、同じ群の層を1つ選んだときの前方割合と比べて初めて言える。フキダシは頁の中で中央 0.152(帰無値 0.500)、前方1割に 33.9%(帰無値 11.2% の 3.0倍)。99.7% が不透明度 256・99.6% が可視・99.8% が通常合成。

そして同じ層が、親の中では後ろ寄りである(中央 0.750)—— 文字がその上に乗るからで、どちらも正しい。頁の中と親の中は別の量なので、同じ列名に入れない(scope の列で分ける)。2つの統計量が食い違うことも在る:親の中では中央が後ろ寄りを言い、前方1割は帰無値どおり(1.04倍)。片方だけ書くと、書いた側の話になる。
ホワイトは逆の形 —— 頁の中では前方1割が帰無値の 0.39倍(手前に寄っていない)が、親の中では 1.8倍。rendering_*(経路2)は頁の中で後ろ寄り(中央 0.721) —— 背景のレンダリングで、線画を隠す側ではない。

帰無値には実測の形が付いている —— 解析の 0.500 は定義から出る数で、定義が間違っていても 0.500 になる。前後に寄る理由の無い名前(線画 22,690層)を同じ軸で測ると中央 0.508で、軸そのものが素直だと分かる。ただし同じ対照は前方1割では帰無値を下回る(0.048 対 0.112)—— 頁の最前は特定の種類の層が占めている。だから前方1割の比は解析の帰無値に対する比として読み、対照に対する比としては読まない。

語彙全体の数と、1名の数は別の量である —— フキダシは語彙9名で中央 0.152、フキダシ 1名で 0.143。正規化は同じで、違いは語彙の広さだった(基盤が独立に再現して出た食い違い)。どちらかを選ぶのではなく、両方を行に出している(matched_on)。
そして早い年の分割形は後ろに居る:1名以外の 268層は中央 0.247 で、面と輪郭に分かれた2名は互いにほぼ同じ深さ(0.244 / 0.252)—— 組として、後の単層形より後ろに在る。

この表が答えないのは「何を隠しているか」である —— 手前に在ることは、重なっていることではない。小さい層も透明な層も手前に在る。画素の実測は保留中(覆いの定義・帰無値・事前登録が先)。そして opacity = 256 は層の設定で、画素のアルファではない。向きは供給元の v2 の訂正に依っている(v1 は z_global を逆に書き、CSV は正しかった)—— こちらでは兄弟の order_in_parent との一致でしか確かめていない。

重複は3つの別の量 —— 引き算で作った数は、引き算の意味を名前に持たない

7,667 − 6,194 = 1,473 を「複製の数」と書くと、2,458 を 1,473 と報告する。A − B は量ではなく手続きである。この集計はこの引き算をしない —— 量ごとに行を持つ。全 9,653 行の sha256 が来たので、ここで測った数である(ハッシュ自体は抽出側が計算した列)。
