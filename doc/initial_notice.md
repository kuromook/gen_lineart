## この track が存在する理由

Track D が測った通り、**画素の一致を目的にする生成の学習は、条件画像の再現に収束する**。
位置の合ったペアだけで学習しても、条件画像に無い GT の線を描く割合は対照と同じ約10%だった。

一方で、出力の線の **27〜50% は GT にも条件画像にも近くない**。凍結 UNet の癖(クロスハッチ、
描き足された髪の線)である。**「ベースモデルの美」はすでに出力に混ざっているが、誰も制御して
いない。** 本プロジェクトはそれを一貫して「幻覚」として扱ってきたが、常に悪いのかは確かめて
いない。

GT と条件画像が食い違う場所は、どの目的関数も定義していない空白地帯である。ここを
「人が見て良いと思う方」に倒せるなら、Track C の選択にも、生成の微調整にも使える。

## この track の問い

**「線画として良い」を、人の判断を再現する形で採点できるか。**

できたら接続先は3つ(この順に安い):
1. Track C の同点決着(GT が答えを持たない場所の、残す/消すの判断)
2. 推論時の空間制御(条件画像が当てにならない領域だけ ControlNet 強度を下げる)
3. 報酬による微調整(DRaFT/ReFL 系)

## 【2026-10-04】再開済み — 判定待ち(ユーザーの目が必要)

比較UI: **https://claude.ai/artifact/SxvR6wa6nMNAmr6FXR4hV3** (300組、線分単位)
旧・画素単位セット(77件判定済み、差し替え済み): https://claude.ai/artifact/CF5bePbbC2YBRmvLfeLJqo
記録: `results/trackc_judge_20261004/`、詳細は `doc/work_log.md` の 2026-10-04 の節。

Track C の削除を**ラフ画像に投影**して判定可能にした(分類器が動くのは条件画像のインクでは
なく `edge_map(条件画像)` で、輪郭マップのままでは1本の線が両側の輪郭2本に見えるため
線画として読めない)。5アームすべて同じ描画・同じ下絵で、違うのは**どのインクが消えたか**だけ。

**【同日改訂】削除は画素単位では判定できない。** 最初の画素単位セットは77件でユーザーが
中断。「雪のような白い粒」＝線が破線化したもので、全アームに出る(classifier 38.6%、
placebo 52.1%、**オラクルですら34.0%**の線分を壊す)。しかも選ばれた側が「破線の少ない側」
だった割合は23/24で、優位カウントと完全一致した。つまり**どの線を選んだかではなく
どちらが線を壊していないかを測っていた**。削除判断を**線分単位に集約**して作り直し
(丸ごと残す/丸ごと消す、破線は全アーム0.000)。

判定3種(読む順も事前登録):
1. `oracle vs placebo_oracle` — **計器チェック**。理想的な削除を同量のランダム削除より
   良いと感じられなければ、この材料では何も読めない。最初に見る
2. `classifier vs placebo` — **本題**。インク量も削除断片のサイズ分布も一致済み
3. `classifier vs rough` — そもそも消して良かったか。唯一インク量を揃えられないので別建て

読み出しは `tools/analyze_trackc_judgements.py`。合格条件は変更なし。

**ついでの発見**: Track C の +0.0272 は描画の違う基準線との比較だった。正しい基準線
(`keep_all` = 何も消さない輪郭マップ, signal 0.16078)に対しては **+0.0320**。結論は
覆らない。退化アーム -0.02104 で lesson 9 の規約も通過。Track C へ通達済み。

## 【2026-09-17 — 上記により解消済み】収集を中断していた — 材料がまだ存在しない

材料の側にも証拠がある。段階1のために用意した3候補のうち、線画として成立しているのは
**前処理器単体だけ**で、残りは学習済みモデルの出力(中間調の割合 `preproc` 0.072 に対し

## 次の一手(順序つき) — 【2026-10-04 に段階1を再開、上記参照】

### 1. 判定データを集める(最初の一手)

素材はすでにある。Track D のスナップショット出力、前処理器単体、削除オラクル、GT。

- 比較2枚組を作る。**同一タイル**の異なる出力同士を並べ、どちらが線画として良いかを選ぶ
- 比較 UI は Artifact(保存機能つき)。1回数秒、目標 300〜500 組
- **同じ組を再提示して本人内の一貫性を測る。** 採点器の上限はここで決まる
- 「どちらとも言えない」を選べるようにし、曖昧な組は学習から外す
- 組の作り方に偏りを入れない。時点・群・タイルを層化して選ぶ(片方が常に白い等の手がかりで
  選べてしまうと、採点器は質感だけを覚える)

### 2. 採点器を作り、検証する

- まず既存の線画らしさ軸(`near_white_frac`/`line_width_p50`/`fill_ratio`/連続性/交点統計)を
  特徴量にした軽い線形モデル。次に小さな CNN か CLIP 特徴＋線形
- 評価は **hold-out の人の判断をどれだけ再現するか**だけ
- **合格条件(先に決めてある)**: hold-out 一致率 ≥ 本人内一貫性 × 0.85、かつ既存の単独指標
  (f1 / near_white / fill)より明確に高いこと
- **落ちたら 3 に進まない。** 指標に3回裏切られたプロジェクトなので、ここで止まれることが設計の一部

### 3. 用途に接続する(合格後)

Track C の同点決着 → 推論時の空間制御 → 報酬微調整。学習が要るのは最後だけ。

## 運用ルール(Track A〜D で確立、引き継ぎ)

- **数値だけで判断しない。** 必ず目視モンタージュを作り、画像の正確なパスを数値と併記する。
  画像は`/tmp`ではなく`results/`配下
- **`gt_bsds_f1`を報告するときは条件画像自体のスコアを基準線として併記**(共通基盤 lesson 6)
- **プールを跨いで平均しない**(`lineart`系と`housei`系は別タスク)
- **学習損失で進捗を判断しない**(lesson 7)。スナップショットごとに hold-out を採点する
- **条件画像は学習用ペアでも中身を測る**(lesson 8)。評価セットだけ見ると分布のずれを見落とす
- 大きな学習・抽出は必ずスモークテストしてから本番投入
- 長時間 GPU ジョブは月〜木の4日連続バッチが標準枠
- バックグラウンド実行は`setsid`で完全に切り離す(PPID=1を確認)。`pkill -f <スクリプト名>`は
  自分のシェルにも一致して自滅するので PID を特定して`kill`する
- 線を単位にする処理で共有の`evaluate_stroke_stability.skeletonize()`を使わない
  (2px幅が残り交点判定が壊れる)。skimage の1px細線化＋crossing number を使う
- `bipartite_match_f1` は特定のタイルで数分〜12分以上かかることがある。多数タイルに一括適用
  するときはタイルごとにサブプロセス化してタイムアウトを設ける
  (`tools/evaluation/vae_roundtrip_score.py` の方式)

## 共通基盤からの通達: f1 の読み方が変わった (2026-10-03)

**再開するときに読んでください。このtrackの過去ログにある `gt_bsds_f1` の値は、
そのままでは比較に使えません。**

`gt_bsds_f1` には**床**がある——入力と何の関係もない絵でも、密度があれば2pxの
一対一マッチングはどこかに当たる。しかも**床は定数ではなく出力ごとに違う**:
同じ退化出力の床が `holdout_lineart_family` で0.1941、`diag_valid5` で0.1285、
houseiで0.1027。**密度だけの関数でもない**(ink 0.425で床0.148、ink 0.443で0.204
——線状の墨は当たりにくく、面に散ったハッチは当たりやすい)。

報告すべきは生のf1ではなく **signal**:

```
signal = f1(出力, 自分のGT) − 平均_j f1(同じ条件の別タイル出力_j, 自分のGT)
```

GTを固定して予測の中身だけ入れ替える置換帰無。実装は
`../lineart/tools/evaluation/measure_f1_signal.py`(GPU不要、ディスク上の既存出力に
遡って適用可)。詳細は共通基盤 `doc/CURRENT.md` lesson 9。

**検証規約**: 新しい条件を測るときは必ず退化出力も同じ手順に通し、その signal が
0近傍に出てから他を読むこと。

**houseiプールについては追加の警告**: このプールでは `gt_bsds_f1` がほぼ判別能力を
持ちません。**正解のGT線画そのものを入れても signal は +0.0657 しか出ない**
(近白タイルが38%あり、空白同士が高いf1で一致するため)。houseiでのf1比較は、
プールを跨ぐ跨がない以前に意味を持ちません。

このtrackが主に使っている指標(AUC・トークン統計・語彙の信頼性など)は
この問題を持ちません。影響するのは過去ログに残る f1 の数値だけです。

## 共通基盤からの通達: 再開条件が満たされました (2026-10-03)

**このtrackを再開します(ユーザー判断)。** 停止理由は「軸が悪い」ではなく
「比較に足る材料が無い」で、再開条件は上に書いてあるとおり
**「両方が解釈可能な出力の組が作れるようになったとき」**でした。

### なぜ条件が満たされたか

**Track C(`../lineart-stroke-selection`)の削除分類器が、その組を作りました。**

本trackが停止した時点では、解釈可能な出力が前処理器のものしか無く
(midtone 0.072 対 学習モデルの 0.503 / 0.259)、組にすると
「きれいな線画 対 壊れた何か」にしかならなかった。

Track C の分類器は**構造上、削除専用**です(`to_keep_mask()` が条件画像の
インクの外に絶対に出ない)。したがって**出力は条件画像のインクの部分集合**で、
条件画像が解釈可能である以上、**その部分集合も解釈可能**です。
壊れた出力ではなく、**同じ線画から線を間引いたもの**になります。

- 条件画像 `lineart_coarse`: ink 0.055
- Track C 分類器: ink **0.042**(消すべき線の37%を実際に削除、`c_survival` 1.0→0.6283)

### 判定してほしいこと(一点)

**「分類器が消した線は、消して良かったのか」。**

これは本trackが最初に立てた問いそのものです——briefing の上の方に書いてある
「**GT と条件画像が食い違う場所は、どの目的関数も定義していない空白地帯**」。
Track C の削除は、まさにその空白地帯での選択です。

### なぜ急ぐ価値があるか

Track C は signal を **+0.0272** 改善しましたが、**同時に recall が 0.169
落ちています**。「削るべきものを削った」のか「削りすぎて指標だけ得をした」のかは、
**数値だけでは決着しません**。しかも判定に使っている物差し(signal、lesson 9)は
**2026-10-03にできたばかり**です。

本プロジェクトは指標に3回裏切られています(orientation_entropy 単独、f1 単独、
near_white 単独)。**Track C は現在この+0.0272を根拠に構造変更へ進もうとしており、
人の目が支持しない改善に最適化し続けるリスクがあります。** それを止められるのは
このtrackだけです。
