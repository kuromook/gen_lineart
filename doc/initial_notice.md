## この track の目的

**ラフからベタ塗り(黒く塗りつぶされた領域)を予測する。** 線の精細化ではない。

なぜこれをやるか。本プロジェクトの常態は「**学習した全モデルが前処理器単体に負けている**」
(共通基盤 lesson 6)で、残差は2つに分かれている —— 削除(lesson 10 で閉じた。
理想的な削除でも人には使えない)と**ベタ塗り**。後者は性質が違う:

- 前処理器(`LineartDetector`)の `fill_ratio` は **0.0%**。GT は **24.5%**
  (**どちらもインク正規化値**。タイル面積に対する割合では 4〜8%。両者は換算できない —— 面積を測るマスクは、この比が数えている核を膨張させたものだから)
- **エッジ検出器は原理上塗れない。** だからここだけは「前処理器に負ける」が構造的に起こらない

つまりこの track は、**勝てば構造的な勝ち、負ければ「塗りは別プロジェクト」が確定する**
という形になっている。項目5が問うていたのはまさにそれ(「計画の残り半分なのか、別の企画なのか」)。

## 禁止事項(明示)

1. **diffusion / ControlNet でベタを描かせようとしないこと。** Track D の仮説4
   (`../lineart-pair-signal`)は「**条件画像に無い GT の線はモデルが描かない**」を支持して閉じた。
   ベタは条件画像に 0.0% しか無い。lesson 8(目的関数は条件画像の再現に収束する)と合わせると、
   この系列は**構造的にベタを出さない**と予測される。使いたいなら、先にその予測を反証する
   器具を作ってから登録すること
2. **CNN+GAN(`scripts/train_i2i_survey.py` の msgan/cleanup 系)への復帰はしない。**
   lesson 5 で降りたアーキテクチャ。線を綺麗にする仕事はこの track の担当ではない
3. **前処理器のベースラインを併記しない数値を報告しない**(lesson 6)。ベタについては
   前処理器の値が 0.0% なので、**「塗らない」という自明なベースラインも必ず併記**すること
4. 事前登録の合否基準を事後に緩めない。目視図は `results/` に置く(`/tmp` は禁止)
5. `near-blank` タイルを混ぜたまま平均を報告しない(下記のデータの注意を参照)

## 段取り(2段。第1段は作者の目を要さない)

### 第1段: ベースライン測定(GPU 推論のみ)

**この2プールは一度も評価されていない。** 数値が無いまま学習を始めると、あとで何と比べるのかが
決まらない。まず次を測る:

- 前処理器単体(`LineartDetector`)を `housei`/`ako5` に通し、`fill_ratio` と paper profile
- 既存の採用チェックポイント `checkpoints/combined_koma_lucy_mild_msgan_20260729`
  (`scripts/inference_i2i_batch.py`)を同じプールに通す —— **lineart プールで学習したモデルが
  ベタのプールで何をするか**は誰も見ていない
- 指標は「線の f1」ではなく**ベタ領域そのもの**: GT のベタマスクに対する IoU / F1、`fill_ratio` の差。
  線側は `stroke_decomposition.py`(lesson 9)、`bsds` を使うなら必ず
  `tools/evaluation/bsds_guard.py` 経由(素の `bipartite_match_f1` は最悪時間が無限)
- **near-blank 層と通常層を分けて報告**。全体平均は併記してよいが主値にしない

走らせる前に `doc/work_log.md` へ事前登録する。器具確認に**既知の値のセルを1つ**入れる
(例: `pool_inventory.csv` の `fill_ratio` を自分の実装で再現する)。

### 第2段: 領域予測モデル(月〜木の4日枠)

入力=ラフ、出力=**ベタマスク**。「どの閉領域が黒いか」という領域予測で、線を描く課題ではない。
ベースラインを3つ**必ず**置く:

1. **塗らない**(fill IoU = 0、`fill_ratio` 誤差 = GT の全量)
2. **前処理器の閉領域を全部塗る**(上限側の自明解。過剰に塗ると何が起きるかを見る)
3. **GT の平均塗り率だけ、面積の大きい領域から塗る**(「量は知っているが場所は知らない」統制)

合否基準は**結果を見る前に**固定する。1 と 3 の両方を超えなければ、それは勝ちではない。

作者の目は最後に回す。Track E の教訓(lesson 11): 壊れた出力同士の比較は損傷を順位づけるだけ。
数値で 1 と 3 を超えてから目視に出す。

## 共通基盤からの訂正 (2026-10-10): 上の表の 2 数値はこちらの誤りでした

本trackの 2026-10-09 の指摘(事前登録の末尾)を受け、**共通基盤側の記録を訂正**しました
(`a8873bb`)。本ファイルも上の該当箇所を直してあります。

1. **枚数**: `ako5` は **5,962**(6,380 ではない)。`ls | grep -c "^ako5"` が `ako5r` も拾い、
   418 を二重計上していました。合計も `housei` test 1,596 を落としていたので、
   **正しくは train 11,450 + test 1,596 = 13,046 枚**。アンカー付きで数え直して確認済み。
   「未学習・未評価」という主張自体は変わりません
2. **`fill_ratio` はインク正規化**で面積率ではない、という本trackの指摘を採用。共通基盤の
   Next Actions 項目5 と台帳の両方に、**面積率 4〜8% を併記**し、
   **乗算では換算できない**(面積マスクは核の膨張)ことも書きました

**一般形として記録に残したもの**: 「**量を書いていない数値は、読む側が期待する量として読み直される**」。
2026-10-09 に Track G が共通基盤の「16〜20%」で同じ失敗を踏んでおり(占有率 対 切り詰め割合)、
2日で2件・別trackから・別ファイルで出たので、本プロジェクトの記録の主要な失敗様式として扱います。
**本trackが数値を報告するときも、量・分母・母集団を必ず併記してください。**

あわせて、**スモークで前処理器の閾値問題を見つけて、本走の前に事前登録を
「自分の見出しが出にくくなる方向へ」修正した判断は正しい**です。
`preproc@budget`(インク量を正解から渡して置き場所だけ検出器に決めさせる)が入ったことで、
C1 は自分の閾値の同語反復ではなく「エッジ検出器は原理上塗れない」の真の検査になりました。
