## Context

Track F は本来「線画を構成する1単位=線に特徴量を与え、その組み合わせで絵ができているとみなし、
GPT の文章生成になぞらえて線画の生成を目指す」track だった。ところが最初の initial notice が
この目的を**「この線はこの配置に在るべきか」という判別問題**に変換してしまい、以後4つの実験が
すべて合成負例(ずらし/回転/別由来)の判別に費やされた。結果は位置の判定 0.50〜0.60、
種類の異常 0.81〜0.84 で、合格条件(0.80)には一度も届いていない。

2026-09-18、ユーザーが目的を明示的に再定義した。

- 線=単語または1文字、絵(**コマ**)=文章。**この方式で生成を目指す**。判別は目的ではない。
- **480pxタイルは使わない**(断片化されすぎ)。**下絵(条件画像)も使わない**(構成が不明瞭、ノイズ)。
- ペアでない線画のみのデータセットを投入してよい。
- 文章と違い**順序は存在しない**。「最後の線を1本抜いた絵から、妥当な1本を予想させる」作りが要る。
- コマ内の複数の線の塊(クラスター)が**単語や文にあたる意味単位**になっているはずで、それを見極めたい。
- VLM/タガーは**語彙付けにも使う**(全コマにWD14タグ)。両方の系統を並行で進める。

この計画は、その再定義に沿って Track F を組み直す。旧 notice は
`doc/archive/initial_notice_discriminative_20260918.md` に退避済み、
`doc/initial_notice.md` は生成路線に書き換え済み。

### 追加で判明した欠陥(2026-09-18、検算済み)

**`make_negatives.order_path()` は多区間の線を最初の隙間で打ち切っている。** 交点の画素は
どの線にも属さないため、2区間以上を繋いだ線は画素が連続せず、8近傍で歩く`order_path`は
最初の区間だけ返して止まる。実測(無作為4コマ):

| コマ | 線 | order_pathが残した割合 | 1割超を失う線 | 2区間以上の線 |
|---|---:|---:|---:|---:|
| koma_0051_page0013_p4 | 1,069 | 0.657 | 25.4% | 23.6% |
| koma_04533_068_2024b_ako | 206 | 0.628 | 25.7% | 26.2% |
| koma_03304_041_2021_akog | 732 | 0.623 | 22.1% | 20.9% |
| koma_00847_011_2017_ako5 | 131 | **0.492** | 47.3% | 44.3% |

コーパス統計(2区間以上の線が26.2%、全骨格長の56.4%)と整合する。つまり
**`results/panel_tokens_20260918/` の折れ線は平均して線の半分**であり、
`results/stroke_transformer_*` の2回の学習もその上で回っていた。
上の再現率0.38〜0.91の主因はここ。

**結論: 表現(骨格+幅)は十分で、失っているのは線への抽象化の側**——区間の打ち切り(最大)、
ヒゲ除去、`min_len` 未満の切り捨て、交点画素(どの線にも属さない)、16点への再標本化、線ごとに幅1つ。
インクの18〜92%が「ベタ」(幅8px超)で、ベタの多いコマほど中心線+幅での再現は効くが、
細い線主体のコマでは16点の折れ線が曲率を落として2pxに収まらない。

**この gap を閉じるまで、生成の議論は成立しない**(生成したトークンを絵に戻せないため)。

## 設計: 4本の柱

### 交点の定義(`tools/stroke/strokes.py` の現行仕様。修復はこれを前提にする)

1. 骨格は1px(`skimage.skeletonize(ink_mask(gray))`)。
2. 各骨格画素で8近傍の輪を一周し、**0→1の変化回数(crossing number)が3以上**なら交点画素。
   近傍数ではなく変化回数を使うのは、1pxの階段状の斜め線の誤検出を避けるため。
3. 交点画素を3×3膨張して骨格と交差 → **連結成分ごとに1つの交点クラスタ(ノード)**。
4. ノードを除いた残りの8連結の連なりが**区間(span)**。
5. **ノードの画素はどの線にも属さない**(これが打ち切りの原因)。
6. 2つのノードを繋ぐ短い区間(長さ ≤ max(3, 局所インク幅×1.5))は「橋」とみなし両ノードを統合。

実測(無作為4コマ): ノードは**中央値4px / p90 4〜5px / 最大8〜12px**、骨格の**2.8〜3.4%**。
埋めるべき隙間は4px程度なので、**区間の端点どうしを直線で繋ぎ、ノードが6px超のときだけ
重心を経由**させれば、2px許容の測定に耐える。

注意: これは**骨格の交点**であって絵の交差ではない。ベタでは中心軸が木状に枝分かれして
交点が大量に出る(GTで1.5%に対し前処理器出力では5.1%)。面トークンを分ける根拠でもある。

### A. 表現の忠実化(最優先・CPU)

トークンの語彙を決める前に、**コマ → 線 → 描き直し**で元の絵が戻ることを保証する。

修復は効果の大きい順に段で行い、**段ごとに同じ60コマで測り直す**(どの段が効いたかを残す)。

| 段 | 直すもの | 見込み |
|---|---|---|
| R1 | **区間を交点の重心を経由して繋ぐ**(打ち切りの修復)。`order_path`は区間ごとに使い、区間どうしは端点の最近接で連結 | 回収 0.5→0.95 付近。最大の効き |
| R2 | 点ごとの幅 | インクのF1 +0.10、IoU +0.15(実測の上限比較より)。交点の穴もほぼ埋まる |
| R3 | 点数を長さに比例(16〜64点) | 300px超の線だけ。全体の0.4%程度 |
| R4 | 未割当の骨格(交点・ヒゲ・橋・短い線)を接合トークンとして持つ | R2で大半が埋まるので残りの詰め |
| R5 | ベタを面トークンに(下記) | ベタ率の高いコマで効く |

- 点の数を長さに比例させる(8px毎程度)、**点ごとの幅**を持たせる。
- **すべての骨格画素をいずれかのトークンに帰属させる**: 交点クラスター、ヒゲ、橋、
  `min_len`未満を捨てずに、短トークン/接合トークンとして持つ。
- **ベタは別種のトークンにする(ユーザー決定 2026-09-18)**。語彙を「線」と「面」の2種類に分ける。
  面トークン = 閉じた輪郭(点列)+塗りつぶしの指定。幅8px超が支配的な連結領域を面として取り出し、
  その輪郭を点列で持つ。残り(細い部分)は従来どおり線トークン。
  面と線の境界の閾値(幅8px)は、再現率と、面として取り出した領域の目視で妥当性を確認する。

**事前登録の合否**: 無作為60コマで **回収 ≥ 0.95 かつ 描きすぎ ≤ 0.02**(2px許容)、
かつモンタージュ(原画|描き直し|差分)を見て線画として同じに見えること。
届かない場合は、原因別に1回だけ作り直す(点密度 / 幅の持ち方 / ベタの扱い)。
2周目で届かなければ、線という単位そのものを疑う材料として記録し、ユーザーに判断を戻す。

### B. 穴埋め予測(GPUの本線)

順序を捏造せず、**1本(のちにk本)抜いた絵から、抜けた線を当てる**。

- 入力: コマの残りの線すべて(集合)。既存の `train_stroke_transformer.py` の
  エンコーダとデータローダを流用(69次元特徴、8〜1024pxの正弦波位置、可変長+マスク)。
- 出力の形は2段階で検証する。
  1. **位置の予測**: コマを粗い格子に分け、抜けた線の重心がどのマスかを分類する。
     まず「どこに」が当たるかだけを見る。
  2. **線そのものの予測**: 位置に加えて、向き・長さ・曲率・幅を回帰(または量子化して分類)。
- 評価は AUC を使わない。
  - held-out の**尤度**(bits/線)
  - 位置の**上位k精度**(正解マスが上位k件に入る割合)
  - **描画して目視**: 抜いた線・モデルの予測・正解を重ねたモンタージュ
- **必ず併記するベースライン**: (a) 一様分布、(b) そのコマの線の分布だけから予測
  (位置の周辺分布)、(c) 最寄りの線の延長。これらを尤度で明確に上回らなければ、
  「関係を学んだ」とは言わない。

**事前登録の合否**: 位置の予測で、ベースライン(b)より **尤度で 0.5 bits/線以上**改善し、
上位10%のマスに正解が入る割合がベースラインの2倍以上。目視で「もっともらしい位置」に
見えること。1周で判断し、落ちたら入力表現か課題設定のどちらが原因かを切り分けてから次に進む。

### C. 意味単位(クラスター)の実在確認(CPU)

「線の塊が単語にあたる」が測れる形になっているか確かめる。

1. **グラフを作る**: 線をノード、端点の近接・接触・平行・共有する交点をエッジにする。
   `networkx` は導入済み(sklearn と faiss は無い)。
2. **塊を取り出す**: 連結成分では粗すぎるので、モジュラリティ最大化
   (`networkx.algorithms.community.greedy_modularity_communities` など)で分割する。
   塊の大きさの分布、コマあたりの個数を出す。
3. **繰り返しを測る(語彙の実在テスト)**: 塊を位置・大きさ・回転で正規化し、
   塊どうしの距離(例: 形状記述子のユークリッド距離)で近傍を探す。
   **別のコマの塊と近い塊がどれだけあるか**が、語彙が実在するかの指標。
4. **目視**: 頻出する塊を並べたモンタージュを作り、人が見て「目」「髪の束」「輪郭」と
   言えるかを確認する。

**事前登録の合否**: (i) 塊の大きさが2〜30本に集中し、コマあたり10〜60個程度で、
連結成分とは明確に違う分割になっていること。(ii) 塊の**30%以上**が、別のコマに
一定以上似た相手を持つこと(偶然水準は、線を無作為に組み替えた対照群で測って併記)。
どちらも落ちたら「意味単位は現時点の幾何では取り出せない」と記録し、Bに資源を寄せる。

### D. 語彙付け(CPU、Aと並行で流せる)

- **WD14タグを全5,345コマに付ける**。`scripts/tag_wd14.py --file-list ... --image-dir ...`、
  CPU 1枚1.2秒、約1.8時間。出力は `results/panel_tags_<date>/panel_wd14.csv`。
  用途: コマの内容ラベル(後で条件付き生成や、塊とタグの対応を見るのに使う)。
- **Qwen3-VL(Ollama、起動済み)** は検証にのみ使う: Cで出た頻出クラスターを
  切り出して「これは何に見えるか」を少数サンプルで尋ね、幾何的な塊が人の見る単位と
  一致しているかを確かめる。生成物が線画に見えるかの判定にも後で使う。
  既存の呼び出し例は `tools/pair_extraction/vlm_review_hamlabi_regions.py`。

## GPUの使い方(2026-09-18、連休のため平日ルールを解除)

**ユーザーの見立ては正しい。今の作り方では SD/SDXL のような長いジョブは出てこない。** 実測:

| | 実測値 |
|---|---|
| モデル | 480万パラメータ(d=256・6層) |
| GPUメモリ | 912MB / 12GB |
| GPU使用率 | **17%**(CPUのデータローダ律速) |
| 1エポック | 62〜76秒(学習3,982コマ) |
| 30エポック | **約35分** |

1線=1トークンだと1コマ約300トークンしかなく、GPUが遊ぶ。**いま重いのはCPU側**
(細線化2時間、書き出し50分、WD14 1.8時間、psd_line抽出1〜2時間、グラフとクラスター半日)。

**長いGPUジョブが正当になるのは次の3つで、いずれも表現が固まってから。**

1. **1線=十数トークン(点列)にする**と1コマ約4,700トークン。実測の外挿
   (d=512・12層で16,000トークン1.08秒/step、32,000トークン3.86秒/step)から
   **1エポック25〜30分、30エポックで12〜15時間**。これが最初の「長いジョブ」。
2. **語彙をVQで学習する**(形のコードブック)。中規模、数時間。
3. **生成の本番**(線+面の全語彙、psd_line合流後、モデルを大きくする)。数日規模もあり得る。

**連休の使い方の方針**: 今日はCPUの前処理を並行で走らせ切り、短いGPU実験(35分×数本)で
課題が成立するかを確認する。成立したら、夜通しで長い1本(12〜15時間)を回す。
**先に長いジョブを回さない。** 今日見つけた打ち切りバグ(線の半分しか入っていなかった)が
まさにその失敗の実例で、壊れた表現で12時間を捨てるのが最悪の使い方になる。

長い1本を回す前にやること: **トークンをメモリマップの配列に事前展開する**
(現在GPU使用率17%はデータローダ律速なので、長時間回すなら先に外す)。

**投入の権限(ユーザー決定 2026-09-18)**: 短い検証が**事前登録した基準を満たしたら、
確認を取らずに長い1本を投入してよい**。翌日にまとめて報告する。基準を満たさない場合は
投入せず、原因の切り分けを報告する。

**長い学習に入れるコーパス(同)**: psd_line をコマ単位で抽出し、**目視で切れ方が妥当なものが
8割以上なら合流**させる。足りなければ既存5,345コマのみで回し、psd_lineは切り方を直してから
次の回に入れる。合流した場合は、出典ごとの内訳を結果に必ず併記する
(`clip_pairs_v3`が9割を占める偏りは既知で、psd_lineはその希釈になる)。

## この計画が答えを出す問い(順に)

1. 線と面のトークンで、元の絵は戻るか(A、E)。
2. 線の塊は実在し、別の絵にも繰り返し現れるか——つまり**語彙はあるか**(C)。
3. 抜けた1本を、周りの線から当てられるか——つまり**文法はあるか**(B)。

3が通れば、抜く本数を増やしていくことで生成に連続的に繋がる。1本も当てられないなら、
その時点で「線の組み合わせで絵ができている」という前提自体を問い直す材料になる。
