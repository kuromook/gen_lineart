## 【2026-09-17】再開に向けた見直し(ユーザーとの議論、未着手)

停止の原因を、特徴量ではなく**単位の取り方**に求め直している。

1. **線画と下絵のトークン化に本質的な差はない。** 下絵は線が多く、無駄な線・滲み・ぼけ・
   消しゴムで薄くなった線を含むという程度の差。「前処理器の出力はトークン化しきれない」
   (下の節)は、**今の分かち書き器がノイズの多い入力で壊れる**という道具の限界であって、
   性質の差の証明ではない。順序は**線画で単位を固める → うまくいけば下絵へ広げる**。
2. **480pxタイルは U-Net/diffusion のサイズ制約**で、線の意味を切り刻んでいる。線トークンは
   別の空間なので、この制約に従う理由がない。実測(work_log「how large an image can stroke
   tokens handle」): コマは原寸で中央値約4MP・約600〜1,000本、最大40MPで5,386本。
   RTX 3060で線1本=1トークンのTransformerは 37.8Mパラメータで32,000トークンまで学習可能。
   **限界はメモリでなく時間で、コマはもちろんページも収まる。**
3. **文脈の単位はコマ。** コマ=一つの文章、ページ=文章の束。コマ同士の関係(ページ単位)は
   いずれ見たいが、コマ単位が成立してからの話。
4. 【2026-09-17 実施】単位を作り直した。コマ原寸5,631枚を分かち書きし、交点をまたいで
   方向の続く区間を繋いだ結果 **2,316,355本**、1コマ中央値292本、長さ中央値37px
   (タイル単位は27本・28px)。26.2%の線が2区間以上を吸収し、それが全骨格長の56.4%を占める。
   `housei`は調子・ウォッシュ主体で捕捉率0.783、別扱いにする。
   道具: `tools/stroke/{panel_skeleton,strokes,tokenize_panels,summarize_panel_strokes,
   stroke_link_montage}.py`、出力は`results/panel_skeleton_20260917/`(骨格378MB)。
   `stroke_churn.segments()`は大きい画像で計算量が爆発するため書き換えた(28秒→1.8秒/コマ)。
   残る限界: 太い交差は線幅1本分の隙間が残る、交点画素はどの線にも属さない、
   融合したハッチングはレンズ状の輪になる、30px以下の閉じた白領域は埋めている。

## この track が存在する理由

三方向から同じ欠落が指されている。

1. **ユーザーの見立て**(2026-09-15に提示、2026-09-17に再確認): 線画の線は一本一本が
   意味を持ち、線どうしの関係によって見る側が線画と認識する。しかし現在の学習・推論・評価は
   **画素の位置・濃度・勾配・太さしか見ていない。**
2. **Track E が止まった理由**(2026-09-17): 壊れて解釈不能なものを「美しい」とは判断できない。
   美の軸の前に、**絵として成立しているかの軸**が要る。意味のない単語を吐き続ける言語モデルの
   出力を見ても何も言えないのと同じ。
3. **Track D の結論**: 条件画像つきの生成のε目的関数は「条件画像の再現＋調子の調整」に収束し、
   条件に無いGTの線を描くことも、ある線を消すことも報わない。位置の合ったペアで学習しても
   変わらなかった(条件に無い線を描く割合 0.104 vs 0.113)。

三つとも、**線を単位にした、文脈つきの妥当性の尺度が無い**ことを指している。

## この track の問い

**GTの線画に現れる線の配置には規則性があり、それを判別問題として学習できるか。**

「この線は、この配置の中で在るべきか」を、画素ではなく線を単位に、周りの線との関係を見て
答えられるか。

## 設計

### トークン化 — 道具はすでにある

`tools/evaluation/stroke_churn.py` の1px細線化＋crossing number による交点分割。
検証済み(交点2.0%、長さの85.2%が区間に入る)。**共有の
`evaluate_stroke_stability.skeletonize()`は使わない**(2px幅が残り交点判定が壊れる)。

### コーパスの実測(2026-09-17、**学習用8,467枚の全件**)

| 量 | 値 |
|---|---|
| 1タイルあたりの線 | 中央値 27本 / 平均 32.8本 / p10 7 / p90 67 / 最大 181 |
| 8,467枚での総数 | **277,477本** |
| 線の長さ | 中央値 28px / p10 10px / p90 120px / 最大 854px |
| 20本未満のタイル | 36.1% |
| ベタに乗っていない線(`fill_share` 0) | 75.0% |
| 線として扱えるもの(`fill_share` ≤ 0.2) | **233,735本** |

**訂正**: 最初に無作為30枚から「1タイル平均42本・総数約357,000本」と見積もったが、
全件では平均32.8本・**277,477本**だった(約22%の過大評価)。標本が偏っていた。
以下の議論は全件の値で読むこと。

**この数字が設計を決める。** 1枚の文脈は中央値27本しかない。文書としては長文ではなく一文の長さで、
「言語モデルのように次を生成する」には短すぎる。1/3のタイルは文脈が薄いので層化して扱う。
480pxタイルはコマの切り出しなので、線の意味の一部はタイルの外にある(既知の限界。
文脈をコマ単位に広げるかは、段階1の結果を見てから判断する)。

### だから生成ではなく判別で学習する

正例は277,477本(うち線として扱えるものは233,735本)しかないが、**負例はただで無限に作れる**。

1. 前処理器が出したのにGTが採らなかった線(Track Cの削除オラクルがそのまま使える)
2. 別の絵から持ってきた線(タイル不一致の対応付け)
3. GTの線を位置・角度・長さでずらしたもの

判別なら規模が足りる。**生成として学習させないこと**が、この設計の中心にある判断。

### 特徴量は2段。関係を入れないならこの track を立てる意味がない

- **線そのもの**: 長さ、曲率、端点、太さの変化、濃さ
- **関係**: 接する相手と接点の角度、平行な隣と間隔(ハッチング)、端点どうしの近接
  (繋がるはずで切れている線)、囲いを成しているか、局所の線密度

### 前処理器の出力はトークン化しきれない(2026-09-17 測定、3度の検算後)

**トークンはGT(と、合格条件2では学習済みモデルの出力)から取る。前処理器の骨格から
取ってはいけない。**

| | GT | 条件画像(lineart_coarse) |
|---|---:|---:|
| トークン数/タイル | 27 | 262 |
| 骨格の捕捉率(8px以上) | 0.91 | 0.62 |
| 交点画素の割合 | 0.015 | 0.051 |

前処理器の骨格は、密な交点網で繋がった短い破片の集合で、線の集まりではない。その結果、
**骨格を切って選ぶ方式は画素単位の選択に構造的に届かない**(60タイル、同一スクリプト内比較:
トークン方式の上限 0.301 対 画素単位 0.552)。Track Cが連結成分単位で一度到達した結論
(f1 0.24〜0.43で前処理器単体を下回る)を、より細かい交点分割でも再現したことになる。
交点分割をさらに40/20/10/5pxへ刻んでも回収は0.133→0.162までしか戻らない(191タイル)。

**この測定では自分の二値化を2ラウンド測っていた。** `>32`の素朴な二値化は縁のギザギザから
偽の交点と1〜3pxの破片を大量に作る。穴埋めで捕捉率0.42→0.62、上限0.193→0.301まで回復した。
それでもGTには届かない。ここで引用する上限は「試した中で最良の二値化での値」であり、
真の上限ではない。

## 合格条件(結果を見る前に決めてある)

1. **最低限**【2026-09-18 不合格・3回】: GTの線と偽の線を**骨格の幾何だけで**分離できること。
   **AUC ≥ 0.80**。判定は最も難しい「ずらし」単体で行う(回転・別タイル由来は易しく、
   混ぜた平均は実力より高く出るため。結果を見る前に厳格化した)。
   **実測 0.636(1回目) → 0.726(特徴量を作り直した2回目) → 0.570(単位をコマ単位の
   繋いだ線に作り直した3回目)。不合格。2回目の値は単位の作り物だったと3回目で判明。**
2. **本題**: GTの線画と壊れた学習済みモデル出力を同じ尺度で分離でき、既存の単独軸
   (`midtone_frac`など)より明確に高いこと。
3. **接続**【2026-09-17 書き直し】: 当初は「Track Cの削除オラクルの残す/消すを再現できるか」
   としていたが、**その形では測定上不可能**だと分かった(上記)。前処理器の骨格を切って選ぶ
   方式は、画素単位の選択に構造的に届かない。接続を狙うなら、**選ぶのではなく描き直す**
   ——条件画像のインクに線のプリミティブを当てはめる——形になる。これは段階1・2とは別物の
   大きさなので、**合格条件2を通るまで着手しない**。

**1が落ちたら2に進まない。** 指標に3回裏切られたプロジェクトなので、ここで止まれることが
設計の一部。

## 運用ルール(Track A〜Eで確立、引き継ぎ)

- **数値だけで判断しない。** 必ず目視モンタージュを作り、画像の正確なパスを数値と併記する。
  画像は`/tmp`ではなく`results/`配下
- **偶然水準を必ず併記する**(このtrackでは180°回転とタイル不一致の対応付け)
- **プールを跨いで平均しない**(`lineart`系と`housei`系は別タスク)
- **学習損失で進捗を判断しない**(lesson 7)
- 線を単位にする処理で共有の`evaluate_stroke_stability.skeletonize()`を使わない
- `bipartite_match_f1`は特定のタイルで数分〜12分以上かかる。多数タイルに一括適用するときは
  タイルごとにサブプロセス化してタイムアウトを設ける
- 大きな学習・抽出は必ずスモークテストしてから本番投入
- 長時間GPUジョブは月〜木の4日連続バッチが標準枠
- バックグラウンド実行は`setsid`で切り離す(PPID=1を確認)。`pkill -f <スクリプト名>`は
  自分のシェルにも一致して自滅するのでPIDを特定して`kill`する
- 待機ループの`until ! pgrep -f <名前>`も**ループ自身のコマンド行に一致する**ので終わらない。
  `[t]okenize_panels.py`のように文字クラスで自分を外す(2026-09-17に踏んだ)
- 目視モンタージュの窓を「最も密な所」で選ぶと必ずベタ・調子が映る。線の領域を見るには
  中位の密度の窓も併せて出す(2026-09-17に踏んだ)
